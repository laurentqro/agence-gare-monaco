# Postmortem: article translation data loss

**Date:** 2026-07-20
**Severity:** Data loss (unrecoverable), 2 of 10 articles
**Status:** Bug fixed and merged; restoration blocked until 2026-08-01

## Summary

Saving an article in the admin destroyed its eight translated locales. The bug
had existed since the admin form was built, but was invisible because the
translator immediately rebuilt the translations after every save. On 2026-07-20
the Anthropic API spend cap was reached, the translator could not run, and the
deletion became permanent for the two articles saved that day — the site's two
highest-traffic pages.

## Impact

- **id 8** "Quelles sont les conditions à remplir pour s'installer à Monaco ?" (3,718 monthly impressions, position 7.1)
- **id 2** "Les avantages uniques du système fiscal de Monaco" (2,381 monthly impressions, position 6.8)

Both dropped from 9 locales to French only. Every locale URL (`/en/articles/…`,
`/sv/artiklar/…`, and the rest) served French text to visitors and to Googlebot.
16 translated title/body pairs were lost.

French source text was never affected — verified intact on all ten articles,
markdown structure included. The other eight articles retained all 9 locales.

## Root cause

The admin form submits only the French value:

```erb
<input name="article[title][fr]">
<textarea name="article[body][fr]">
```

`title` and `body` are JSON columns holding all nine locales. `assign_attributes`
**replaces** the column value, so submitting `{"fr" => "…"}` discarded the other
eight keys.

This was latent, not new. `enqueue_post_save_jobs!` fires `ArticleTranslationJob`
after every save, which rewrote the missing locales within about a minute — so
the destroy-then-restore cycle looked like normal operation. The API cap removed
the restore half and exposed the destroy half.

Contributing factor: adding `meta_description` to the form (SEO audit work, the
same day) prompted a batch of admin saves that would otherwise not have happened,
which is what turned a dormant bug into an incident.

## Why recovery failed

Checked and exhausted, in order:

- No database backups on the host
- SQLite WAL post-dated both overwrites; no old page images
- Freed pages in `production.sqlite3` contained no residual translated text
- Wayback Machine: one snapshot only (English of article 2, May 2026)
- `archive.agencegaremonaco.com`: serves **French only**; the other locale paths
  return HTTP 200 but render empty/untranslated content, so it is not a source
  for the lost translations

The translations can only be regenerated by re-running the translator.

| ~12:30 | Fix committed with regression tests |

## Resolution

`3dcaf12` — the controller now merges the submitted French value into the stored
hash instead of replacing the column:

```ruby
existing = @article&.public_send(column) || {}
permitted[column] = existing.merge(submitted.to_h)
```

Covered by four regression tests (title, body, meta description, create path).

`3f1e813` — two rake tasks:
- `articles:backfill_meta_descriptions` applies the ten audit meta descriptions,
  keyed by slug, merged, without enqueuing doomed translation jobs
- `articles:translate_pending` re-enqueues translation for stale/incomplete
  articles once API access returns

## Remaining actions

1. **Deploy `3f1e813`** — until then, any admin save still wipes translations
2. Run `articles:backfill_meta_descriptions` in production
3. On/after **2026-08-01** (or once the spend cap is raised), run
   `articles:translate_pending` to rebuild articles 2 and 8
4. Re-submit both URLs in Search Console after translations return

## Lessons

- **A self-healing system hides the damage it heals.** The translator masked a
  destructive bug for months. Any repair loop should be monitored for how often
  it repairs, not just whether it succeeds.
- **Partial-update forms and whole-value columns are a bad pair.** A form that
  edits one key of a JSON column must merge, never assign.

  Audited the other admin controllers during this postmortem:

  | Controller | Permits | Verdict |
  |---|---|---|
  | `admin/articles` | `title/body/meta_description: [:fr]` | **was broken**, fixed in `3dcaf12` |
  | `admin/properties` | `title: ["fr"], description: ["fr"]` | **still broken** — see below |
  | `admin/categories` | `name: <all locales>` | safe |

  `admin/properties` has the same defect and is **more dangerous**: 24 of 27
  production properties carry multi-locale titles, and properties have no
  translator job, so there is no self-healing to mask or repair the loss. Their
  translations come from Immotoolbox sync, so a re-sync may restore them, but
  this should be fixed with the same merge before anyone edits a property in
  the admin. Not fixed here to keep this change scoped to the incident.
- **No backups existed for a production SQLite database.** This incident lost
  only regenerable content; the next one might not. Automated backups are the
  highest-value follow-up from this postmortem.
- **The loudest error is not always the cause.** The API cap message was real
  and irrelevant to the root cause; the actual fault was silent.
